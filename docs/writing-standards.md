# EnchantForge 写作标准

本文档定义 EnchantForge 的三种写作模式：

1. 产品文案：克制、清晰，以用户能获得的能力为中心；
2. 宣传文案：建立冲突、展示证据，适合比赛和演示；
3. 技术文档：准确、完整、可验证，适合 API、规格和开发说明。

三种模式使用同一套产品事实，但承担不同任务。不要在同一个段落中混用多种
模式，也不要为了追求风格改变功能边界。

## 1. 如何选择

| 内容 | 默认模式 | 目标 |
| --- | --- | --- |
| 门户首页 Hero、功能标题 | 产品文案 | 让读者迅速理解价值 |
| 门户功能说明、示例入口 | 产品文案为主，技术说明为辅 | 建立兴趣并提供可信依据 |
| 比赛投稿、演示脚本、发布介绍 | 宣传文案 | 建立问题、冲突和记忆点 |
| API 文档、README 使用说明 | 技术文档 | 帮助开发者正确使用 |
| `specs`、架构决策、边界说明 | 技术文档 | 保持实现和设计一致 |
| Debug、错误消息、运行提示 | 技术文档 | 准确说明状态和下一步 |

当一个页面包含多种内容时，按区块选择模式。例如门户 Hero 使用产品文案，
代码示例和 API 说明使用技术文档，不要让整页强行保持同一种句式。

## 2. 共同事实

无论采用哪种模式，都必须遵守以下事实：

- EnchantForge 为 Vue 应用组织 AI 上下文和可调用能力；
- 信息和函数由应用显式提供，不代表 AI 可以读取整个应用；
- 函数可以注册为 AI 可调用的 capability，但仍经过参数、Policy 和执行边界；
- AI 负责理解、选择和组合，应用负责事实、权限和副作用；
- DOM 扫描是显式启用的兼容路径，不是默认工作方式；
- 未实现功能必须标记为规划，不得写成当前能力；
- 示例中的调用、数据和页面效果必须真实可执行。

产品文案可以省略实现细节，但不能反转这些边界。技术文档必须把省略的机制补全。

## 3. 语言底线

风格不能凌驾于正常中文语序、日常表达习惯和技术逻辑。无论采用哪种模式，句子首先
必须自然、清楚，然后才考虑节奏和记忆点。

### 3.1 使用正常语序

优先使用：

```text
主体 + 动作 + 对象
```

不要为了突出对象，把句子改成翻译腔或无主语的被动表达。

不推荐：

```text
查询、填写和高亮等能力通过明确接口提供给 AI。
```

推荐：

```text
应用可以把函数注册为 AI 工具。
```

技术文档需要更具体时：

```text
应用通过 `useEnchantAction()` 注册函数。Forge 将 capability 导出为模型可以调用的 tool。
```

### 3.2 抽象名词不能代替信息

`能力`、`控制`、`边界`、`价值`、`开放`、`赋能`、`可能性` 等词本身没有错，但不能
只用这些词互相修饰。句子必须说明具体对象和动作。

不推荐：

```text
能力可以开放，控制仍在应用手中。
```

这句话没有说明开放什么、谁开放、控制什么，也没有说明框架实际做了什么。前后两个
抽象分句只是形式对称，不能帮助读者理解产品。

推荐：

```text
应用决定注册哪些函数。Forge 在执行前校验参数和 Policy。
```

检查抽象表达时，继续追问：

- “能力”具体指哪些信息、函数或接口？
- “控制”由哪个主体通过什么机制完成？
- “边界”对应哪个校验、权限或生命周期？
- 删除抽象名词后，句子还剩下什么事实？

回答不了时，应删除该句，而不是换一组近义词。

### 3.3 逻辑顺序先于文字节奏

技术说明通常按以下顺序组织：

```text
谁提供输入 -> 框架如何处理 -> 谁使用结果 -> 产生什么效果
```

生命周期说明按发生顺序组织：

```text
注册 -> capture -> 调用 -> 注销
```

不要为了排比打乱因果、时间或所有权关系。

### 3.4 不强行押韵或对仗

不推荐：

```text
应用明确提供，AI 按需使用。
```

这句话形式整齐，但“提供什么”和“如何使用”都不清楚，正常交流中也很少这样表达。
不要用两个长度接近的分句冒充逻辑关系。

如果信息值得说明，应恢复完整句子：

```text
应用提供字段、状态和页面结构。Forge 在模型调用前组织当前页面的上下文。
```

如果信息不值得说明，直接删除，不要把它压缩成口号。

### 3.5 标点服务语法

不要为了模仿发布会停顿，在主语、谓语和宾语之间随意加入逗号。逗号只用于真实的
语法停顿、并列和层次划分。

可以有意识地使用短句，但短句必须能独立表达完整意思。连续短句如果只剩语气，没有
新增信息，应合并或删除。

### 3.6 朗读检查

提交文案前至少检查：

- 这句话在正常会议或技术交流中是否有人会这样说？
- 主语是否明确，前后是否偷换了主体？
- 动作、对象和结果是否完整？
- 两个分句之间是否真的存在因果、递进或并列关系？
- 去掉逗号、换行和加粗后，句子是否仍然成立？
- 是否为了显得简洁而删除了理解所需的信息？
- 是否只剩下“能力、控制、边界、价值”等抽象词，却没有具体对象和动作？

读起来拗口时，优先恢复自然语序，不要继续增加标点或拆分短句。

## 4. 术语

### 4.1 AI

产品文案和宣传文案默认使用 `AI`。它指向用户感知到的整体能力，可以覆盖模型、
Agent、工具调用和交互界面。

示例：

> 让函数，成为 AI 的能力。

### 4.2 LLM

技术文档在明确讨论语言模型、Prompt、token、tool calling、模型请求或供应商协议时
使用 `LLM`。

示例：

> Forge 将 provider-neutral tools 转换为 OpenAI-compatible function tools 后发送给 LLM。

### 4.3 Agent

只有在讨论规划循环、后端路由、Agent Client 或多 Agent 编排时使用 `Agent`。不要把
所有 AI 功能都称为 Agent。

### 4.4 Capability、Tool 与函数

- 函数是应用实现；
- capability 是 EnchantForge 内部的可执行契约；
- tool 是提供给模型或 Agent 协议的导出形式。

产品文案可以说“让函数成为 AI 的能力”。技术文档必须说明函数需要显式注册，并由
capability contract、Policy 和 executor 约束。

## 5. 产品文案

这里的“苹果风格”不是模仿固定句式，而是遵循一组产品表达原则：克制、聚焦、具体，
先说能力和结果，再决定是否解释机制。

### 5.1 适用位置

- 首页 Hero；
- 章节标题；
- 功能卡片；
- 产品截图标题；
- 发布页面中的关键结论。

### 5.2 写作原则

1. 一个区块只表达一个核心观点。
2. 标题表达一个具体变化、结果或判断，不用抽象名词拼接口号。
3. 正文使用自然、完整的句子，不为了短而省略必要主语。
4. 能用具体名词时，不使用“赋能”“体验升级”“无限可能”等空泛词。
5. 保留足够留白，不在同一屏解释全部架构。
6. 通过信息层级制造节奏，不依靠押韵、排比或重复标点。
7. 宏大感来自能力范围和真实结果，不来自最高级形容词。
8. 界面标题默认不加句号；正文使用完整标点。问号和感叹号只在语义确实需要时保留。

### 5.3 推荐结构

```text
短 kicker

一个清楚的主标题。

一句完整说明。

一个具体结论。
一条支持该结论的事实。
```

示例：

> 先让 AI 看见
>
> 应用知道的，AI 也该知道。
>
> EnchantForge 将应用提供的信息组织成 AI 可以理解的上下文。

能力卡片：

> 让函数，成为 AI 的能力。
>
> 从一次页面交互，到完整业务流程。

### 5.4 避免的写法

不要把短句、逗号和对仗本身当成产品风格：

```text
应用明确提供，AI 按需使用。
```

问题：

- 为了押节奏牺牲自然语序；
- 没有增加信息；
- 像广告口号，不像可信产品说明。

不要用抽象名词制造看似正确的结论：

```text
能力可以开放，控制仍在应用手中。
```

应改成读者可以验证的事实：

```text
应用决定注册哪些函数。Forge 在执行前校验参数和 Policy。
```

不要使用空泛承诺：

```text
释放 AI 无限潜能，全面赋能业务创新。
```

改为说明真实能力：

```text
让函数，成为 AI 的能力。
从一次页面交互，到完整业务流程。
```

不要在读者理解产品前连续否定其他方案：

```text
不靠 Prompt。
不用 Skills。
拒绝 Computer Use。
```

产品页应先建立自己的机制和价值。技术差异可以在后续架构、原则或对比章节说明。

不要用拟人化否定词代替工程机制：

```text
不偷看。
不猜组件。
不偷偷动手。
```

这些标题没有说明信息来源、注册方式、校验过程或审计能力。除非正文能够立即对应一个
明确机制，否则应直接写出事实：

```text
只有应用显式注册的信息才会进入上下文。
Forge 在执行前检查目标、参数 Schema 和 Policy。
Debug 可以查看模型请求、工具调用和执行结果。
```

## 6. 宣传文案

宣传文案可以更有张力，但必须由真实产品能力和演示证据支撑。它不是把产品文案写得
更夸张，而是把问题、转折和结果组织成故事。

### 6.1 适用位置

- 比赛投稿；
- 发布文章；
- 演示视频脚本；
- 路演和演讲；
- 社交媒体发布内容。

### 6.2 推荐结构

1. 一个真实、普遍存在的问题；
2. 现有做法为什么需要重复劳动或缺少上下文；
3. EnchantForge 改变了哪个开发边界；
4. 用真实示例证明；
5. 说明框架价值，而不是只展示某个 Demo；
6. 用一句可复述的结论收尾。

示例骨架：

```text
我们一直在让 AI 回答问题，却反复手工告诉它页面里有什么。

EnchantForge 让应用自己提供上下文和函数。

同一套机制可以填写表单、分析监控数据，也可以驱动完整业务流程。

这不是一个预制 Agent，而是一套让应用获得 AI 能力的开发框架。
```

### 6.3 张力的来源

可以使用：

- 具体工作场景；
- 前后对比；
- 一段真实操作；
- 一项出乎预期但可以验证的能力；
- 简短、有记忆点的观点。

不应使用：

- 没有证据的“颠覆”“革命”“重新定义”；
- 只靠情绪攻击其他技术；
- 把一个示例描述成通用智能；
- 暗示 AI 可以绕过应用权限；
- 用大量互联网黑话代替产品事实。

### 6.4 对竞品和技术路线的表达

可以明确指出差异，但必须先建立比较维度：

```text
Computer Use 从画面推断界面；EnchantForge 使用应用提供的结构和函数。
前者追求跨应用通用性，后者优先保证已有 Vue 应用中的语义和执行边界。
```

不要只写：

```text
Prompt 和 Skills 都不行。
```

批评必须回答：比较的是什么、代价是什么、EnchantForge 解决了什么。

## 7. 技术文档

技术文档首先是工程接口，不承担制造情绪的任务。读者应该能够据此理解行为、编写代码、
定位错误并判断边界。

### 7.1 适用位置

- API Reference；
- 快速开始；
- README；
- `specs`；
- 架构与策略说明；
- 错误信息和 Debug 说明；
- 示例代码旁的实现说明。

### 7.2 写作原则

1. 使用“主体 + 动作 + 对象”的自然语序。
2. 首次出现的概念先定义，再使用简称。
3. 区分当前行为、兼容行为、限制和未来规划。
4. 公共 API 名称、参数、默认值和示例必须与代码一致。
5. 解释触发条件、生命周期、错误结果和副作用。
6. 能引用类型和函数时，不发明另一套抽象名称。
7. 示例应能编译，并体现推荐路径而不是内部实现细节。
8. 避免无主语的被动句和逐字翻译英文形成的语序。

### 7.3 推荐顺序

一个 API 条目按以下顺序组织：

1. 它解决什么问题；
2. 在哪里调用；
3. 最短可运行示例；
4. 参数和返回值；
5. 生命周期和副作用；
6. 错误与限制；
7. 何时使用低层扩展点。

示例：

```ts
const form = defineModel<ShippingForm>({ required: true });

useEnchantForm(form, {
  fields: {
    recipient: '收件人',
    address: '收件地址'
  }
});
```

说明：

> `useEnchantForm()` 在最近的 `<Enchant>` 边界中注册字段 metadata 和
> `field.fill` capability。组件作用域销毁时，注册自动移除。该 capability 只修改
> 表单模型，不提交表单。

### 7.4 避免的写法

被动且缺少主体：

```text
查询、填写、高亮等能力通过明确接口提供给 AI。
```

改为：

```text
应用通过 `useEnchantAction()` 注册函数。Forge 将对应 capability 导出为模型可以调用的 tool。
```

模糊状态：

```text
系统支持 Workflow。
```

如果尚未实现，应写：

```text
Workflow persistence 处于规划阶段，当前 Core 不导出保存或 replay API。
```

过度简化安全边界：

```text
AI 可以调用应用中的任何函数。
```

技术文档应写：

```text
应用可以将任意函数包装为 capability。只有显式注册、通过参数校验和 Policy 的
capability 才会执行。
```

## 8. 同一事实的三种写法

事实：应用可以把函数注册为 AI 可调用的能力。

### 产品文案

> 让函数，成为 AI 的能力。
>
> 从一次页面交互，到完整业务流程。

### 宣传文案

> 给 AI 一个表单函数，它可以填写页面。给它查询、分析和工作流接口，它就能把多个
> 系统连接成一次完整操作。模型负责理解和组合，应用决定它究竟能做什么。

### 技术文档

> 应用通过 `useEnchantAction()` 或 `defineEnchantApi()` 注册函数。Forge 根据
> capability metadata 和 `inputSchema` 生成 tool，并在执行前校验目标、参数和 Policy。

事实：上下文随 Vue 组件生命周期变化。

### 产品文案

> 上下文始终对应当前页面。

### 宣传文案

> 页面打开、弹窗出现、组件离开，AI 看到的上下文也随之变化，不需要为每个页面重新
> 维护一份静态说明。

### 技术文档

> `<Enchant>` 在组件挂载时向 app-owned registry 注册，在卸载时注销。Forge 在每次
> Agent run 前 capture 当前 registration；业务数据变化不会默认触发 snapshot history。

## 9. 审校清单

### 所有模式

- 这句话是否符合当前实现？
- 主语是否明确？
- 一个段落是否只承担一个叙事任务？
- 是否混用了 AI、LLM 和 Agent？
- 是否把计划能力写成已经实现？
- 是否把示例能力误写成框架上限？

### 产品文案

- 标题是否表达了具体变化、结果或判断？
- 正文是否是自然句子，而不是强行对仗？
- 删除形容词后，是否仍然有信息？
- 是否用抽象名词掩盖了没有具体对象和动作的问题？
- 是否在解释自己的产品之前先批评别人？
- 页面留白能否承担一部分节奏？

### 宣传文案

- 冲突是否来自真实问题？
- 每个重要结论是否有 Demo、数据或代码支撑？
- 观众最终记住的是框架，还是某一个示例？
- 是否为了刺激而扩大了权限或能力边界？

### 技术文档

- API 名称、类型和默认值是否与源码一致？
- 示例是否可以运行？
- 是否说明注册和销毁时机？
- 是否说明错误、限制和副作用？
- 当前、兼容、弃用和规划状态是否明确？

## 10. 对写作者的指令

后续任务可以直接指定：

```text
按产品文案标准改写这一段。
按宣传文案标准写比赛投稿。
按技术文档标准说明这个 API。
```

如果没有明确指定：

- 门户标题和首屏默认使用产品文案；
- 投稿、演示和发布内容默认使用宣传文案；
- README、API、规格和代码说明默认使用技术文档；
- 无法判断时优先保证准确，使用技术文档标准。
