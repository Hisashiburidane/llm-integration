### 作品介绍

我最初只是想让大模型填写一个 Vue 表单。真正开始开发后才发现，模型不知道页面有哪些
字段，不知道当前状态，也不知道应用允许它调用哪些函数。开发者只能在 Prompt、JSON
Schema 和业务代码之间重复维护同一套信息。

**EnchantForge 是一个面向 Vue 应用的 AI 集成框架。**应用通过组件或组合式函数显式
提供当前页面的信息与函数，框架在调用时把它们组织成 AI 上下文和原生 Tools。模型负责
理解用户意图与组合工具，参数校验、权限规则和最终执行仍由应用代码负责。

![EnchantForge 门户首页](./01-portal-home.png)

这种方式不要求 AI 从截图中猜测按钮位置，也不要求开发者为每个 AI 功能重新描述整个
应用。组件挂载时注册，卸载时移除；Agent 每次读取的都是当前有效、且由应用主动提供的
上下文。应用可以从一个表单开始，也可以逐步扩展到页面级助手、自定义 Agent Client 和
整个应用的工具注册。

### 它解决什么问题

AI 应用经常把大量精力放在模型、Prompt、Skills 和知识库上，却忽略了一个更基础的
问题：模型完成任务所需的页面事实与软件接口从哪里来。

EnchantForge 把这部分变成可复用的工程机制：

- 表单 Schema 可以生成字段上下文和受约束的填写工具
- 应用函数可以注册为模型 Tools，不需要在每个页面重复声明
- 自定义 Agent 可以获取同一份上下文和工具，不必依赖聊天框
- Policy 在执行前校验工具名称、参数和调用条件
- 页面内 Debug 与 OpenTelemetry Adapter 可以记录模型请求和工具执行

框架不会读取应用没有提供的信息，也不会把所有状态无条件塞进 Prompt。开发者按任务
选择组件、页面或应用范围，在信息充分、请求成本和隐私边界之间取得平衡。

### 已完成的验证场景

第一个场景是自然语言填写快递表单。`useEnchantForm()` 根据响应式 model 和表单
Schema 提供填写工具。用户输入一段混合了姓名、电话、地址和物品信息的文本，模型将其
转换为结构化调用并填写页面，但不会自动提交。

### 同一个框架，三种触发方式

三个场景的入口不同：表单来自用户命令，Dashboard 来自全局助手，坐席辅助来自业务
事件。它们复用的都是 EnchantForge 对上下文、Tools、Policy 和执行过程的管理。

这也是作品的重点。EnchantForge 不是某一个客服、监控或表单 Agent，而是现有 Vue
系统接入 AI 时可以重复使用的基础设施。业务仍由应用实现，框架只处理跨场景都需要的
注册、捕获、导出、校验、执行和观测。

### 完整性与运行方式

仓库按框架、基础示例、完整应用示例、门户和数据工程拆分：

```text
packages/vue           EnchantForge 核心库
examples/vue           最短接入与事件驱动示例
examples/dashboard-vue 可配置 Dashboard 应用
examples/data-sources  公开数据下载、清洗与 SQLite 聚合
website                中文/英文门户与 API 文档
specs                   产品与架构规格
```

核心库支持 OpenAI-compatible API、自定义 LLM Client、应用级 API 注册、低层
`captureContext()`、页面内 Debug 和可选 OpenTelemetry Adapter。Dashboard 数据可以
通过一个命令完成下载、处理、配置初始化并启动开发环境：

```bash
pnpm demo
```

首次运行会下载航空、北京空气质量和 NYC Taxi 公开数据；OpenTelemetry 场景使用官方
Demo 在本地容器中生成观测信号。后续运行会复用已有数据。模型或数据服务不可用时，
示例显示错误，不使用预制回答替代模型执行。

### AI 在开发过程中做了什么

这个项目既使用 AI 编码，也把 AI 接入本身作为研究对象。开发过程中，编码 Agent 参与
了代码检索、实现、测试、文档整理和重构；人的工作不是接受一次生成结果，而是持续通过
实际场景修正抽象。

例如，Dashboard 的实时数据刷新曾错误地推动 metadata version 增长，导致长时间模型
调用结束后无法执行；回答与高亮也曾被实现为彼此隔离的流程；部分业务提示词一度进入
核心库。根据实际运行结果，项目最终明确了三条边界：

- 稳定的页面结构进入 metadata，实时数据通过 Tools 按需读取
- Snapshot 用于规划上下文和调试，不作为整个执行过程的全局锁
- Core 只实现机制，业务语义、状态与副作用由应用拥有

这些修改不是对模型输出的简单采纳，而是围绕同一个产品目标反复实现、验证和推翻错误
设计的结果。项目保留了规格文档、测试和提交记录，可以核对这条演进过程。

### 通用设置

1. 使用 Chrome，关闭收藏栏、通知和无关扩展
2. 推荐窗口尺寸 `1600 × 1000` 或 `1920 × 1080`
3. 浏览器缩放先尝试 `90%`，确保文字仍然清晰
4. 截图前移开鼠标，避免残留 ECharts tooltip
5. 不展示 `.env`、请求 Header、本机目录和任何密钥
6. 按 `Cmd+Option+I` 打开 Chrome DevTools
7. 在 DevTools 中按 `Cmd+Shift+P`，执行 `Capture screenshot`
8. 需要完整长页面时执行 `Capture full size screenshot`

## 视频脚本

建议成片控制在 `75 至 90 秒`，使用一次完整任务串起全部机制，不逐页介绍功能目录。

| 时间 | 画面 | 解说或字幕 |
| --- | --- | --- |
| 0–6 秒 | OpenTelemetry Dashboard 分析完成，多个 Panel 已高亮 | 一个问题，让应用读取数据、回答并聚焦证据 |
| 6–14 秒 | 门户首页与最短接入代码 | 我最初只是想让大模型填写一个 Vue 表单 |
| 14–25 秒 | 快捷输入触发表单填写，提交保持未触发 | 页面提供字段和写入函数，模型生成受约束的工具调用 |
| 25–34 秒 | 切换到 OpenTelemetry Dashboard 并提交问题 | 同一套机制也可以组织整个页面的上下文 |
| 34–48 秒 | 显示读取数据和调用工具的进度，压缩等待时间 | 实时数据不进入 metadata，由 Agent 按需读取 |
| 48–62 秒 | 回答出现，相关 Panel 高亮，其他 Panel 低亮 | 回答和页面操作来自同一轮工具调用 |
| 62–72 秒 | 打开 Debug，展示读取与高亮记录 | Debug 保留模型请求与工具执行记录 |
| 72–84 秒 | 坐席辅助中的 ASR、订单信息、工单和情绪提示 | AI 也可以由业务事件触发，不必从聊天框开始 |
| 84–90 秒 | 回到项目名和仓库结构 | EnchantForge：让 AI 看见应用 |

等待模型返回的部分可以加速或剪短，但不要剪掉用户问题、工具执行和页面结果之间的
因果链。具体服务名称、指标数值和工具结果使用录制时的实际输出，不要后期伪造。
